- 每节我这边控制在 15 行以内。

## 二、Day 2 到底在讲什么

两句话：

- **写入侧**：把一份 PDF 变成一堆带标签的块，存进 Neo4j。（上传时做）
- **读取侧**：你问一句话，从这堆块里挑出最相关的几条，拼成一段证据交给模型。（提问时做）

中间那道界线是 **Neo4j 的 Chunk 节点**：写入到"切片完成、任务入队"为止；真正落库由图谱 worker 干，属于 Day 3，今天不碰。

## 四、各节教案

### 第 1 节 · 切（✅ 已讲）

- **麻烦**：十万字塞不进模型；一刀切在句子中间，两边都不完整。
- **结论**：1000 是上限不是目标，撞到就停；下刀顺序 = 空行 → 换行 → 中文句号 → 硬切；20 字的 overlap 只在必须切碎一段时才补，切在段落边界时并不触发。
- **看哪**：`app/config/document.yaml:5-7`、`app/rag/text_spliter.py:45-49`
- **实证**：1149 字 → 995 + 152，两块无重复字。
- **检查题**：块 1 为什么停在 995，而不是切满 1000？

---

### 第 2 节 · 块身上的三张标签

- **麻烦**：库里不止你一个人的资料；同一份文件可能被传两次；检索时还要能按"笔记 / 文档"筛。
- **结论**：每个块在入库前被打上 `user_id`、`original_filename`、`md5` 三个标记，后面所有检索都靠 `user_id` 做隔离。
- **看哪**：`router/knowledge_service.py:70-73`、`rag/document_handler/processor.py:199-205`
- **检查题**：`user_id` 为什么必须写在**每一个块**上，而不是只记在"文件"那一层？
- **答案**：见附录 B

---

### 第 3 节 · 上传的六个动作

- **麻烦**：上传不是"把文件存起来"，是"把文件变成能查的东西"。
- **结论**：写临时文件 → 算 md5 查重 → 按扩展名解析 → 切片 → 打标签 → `create_task` 入队图谱抽取。
- **看哪**：`processor.py:85-253`（单文件）、`knowledge_service.py:48-83`（多文件流式）
- **注意**：两条上传路径终点一样，写法完全不同；流式那条才有进度事件。
- **检查题**：md5 为什么必须在解析**之前**算？
- **答案**：见附录 B

---

### 第 4 节 · 为什么切片多线程、写入单线程

- **麻烦**：解析 PDF、跑切分都是阻塞活，放在事件循环里会把别人的请求一起卡住。
- **结论**：`ThreadPoolExecutor(min(文件数, CPU))` 并行切片；单线程串行消费（记 md5 + 入队）；队列 `maxsize=10` 做背压。
- **最值钱的一行**：`await asyncio.to_thread(queue.get, True, 0.1)`
- **看哪**：`knowledge_service.py:283-301`、`303-362`
- **检查题**：如果直接写 `queue.get()`（不加 `to_thread` 和超时），会发生什么？
- **答案**：见附录 B

---

### 第 5 节 · 提问第一步：planner

- **麻烦**：不是所有话都该去检索（"你好"不该）；不同问题该查不同地方。
- **结论**：小模型先规划（要不要检索、用哪个工具、查什么），失败三层降级（文本 JSON → 结构化 → 规则兜底），输出还要被钳死：`steps[:2]`、`top_k ≤ 5`。
- **看哪**：`rag/agentic_rag/planner.py:165-266`
- **检查题**：为什么规划用小模型、评估却用主模型？
- **答案**：见附录 B

---

### 第 6 节 · 检索两条路 + RRF（部分讲过）

- **麻烦**：向量擅长"意思近"，遇到编号、专有名词会失手；全文检索擅长精确词，但换个说法就找不到。
- **结论**：一次调用里两路各查 `2 × limit` 条，然后按**名次**融合：`1/(60+rank)`，两路都出现的自然被顶上去。
- **看哪**：`local_retriever.py:54-72`、`graph/storage/neo4j_graph_store.py:674-727`
- **检查题**：为什么不直接比分数？（提示：两路分数量纲不同）
- **答案**：见附录 B

---

### 第 7 节 · evaluator：够不够答

- **麻烦**：向量检索永远返回 k 条，哪怕一条都不相关；没有评估，模型就拿噪声强行回答。
- **结论**：两条规则快路径（无证据 / 含新鲜词）直接判"不可答"；其余交 LLM 判；LLM 挂了就判"可答"——失败时选便宜的那条路。
- **看哪**：`evaluator.py:77-117`
- **检查题**：LLM 不可用时为什么判"可答"，而不是"不可答、去联网"？
- **答案**：见附录 B

---

### 第 8 节 · 拼 context：去重、8 条、6000 字

- **麻烦**：图、文、联网三路证据会重复；全塞进 prompt 会超长、变贵、丢中间信息。
- **结论**：两道去重（`(source,id)` + 归一化内容）→ 最多 8 条 → 6000 字封顶，超了**整条丢弃**而不是截断。
- **看哪**：`evidence.py:17-62`
- **检查题**：为什么超长时整条丢，而不是把最后一条截一半？
- **答案**：见附录 B

## 附录 B：检查题答案

**第 2 节**：检索的最小单位是块，不是文件。检索时按 `user_id` 过滤发生在**查块**这一步；如果只在文件层记 user_id，每次检索都要先关联回文件表，多一次跳跃，也更容易漏。写在每块上，一条 Cypher 就能过滤干净。（同样的道理：A 和 B 传同一份 PDF，md5 一样、Chunk id 可能重复，所以取节点时还要再按 `user_id` 拦一次。）

**第 3 节**：因为多模态 PDF 加载器要把抽出来的图片存到 `data/extracted_images/{user_id}/{md5}/`。md5 算晚了，图片就落到错误的目录，后面拼不回原文。

**第 4 节**：`queue.get()` 是阻塞调用，会把整个事件循环按住——同进程里所有人的请求都停在那儿等你这一个上传。`to_thread` 把等待挪到线程里，`0.1s` 超时让它能周期性地把控制权还回来。

**第 5 节**：规划只干"选工具 + 写 query"，小模型够用且快；评估要判断证据与问题的相关性，需要更强的理解力。代码里留了一句注释：不再复用主模型做规划，因为"那是 39 秒的来源"。

**第 6 节**：向量分是余弦相似度（0~1），全文分是 BM25 一类的打分（无上界），量纲不同，加权没有意义。RRF 只看"排第几"，天然可比。k=60 的作用是把头部差距压平，不让第一名一家独大。

**第 7 节**：评估失败的两种取向各有代价。判"可答"的代价是偶尔漏一次联网；判"不可答"的代价是每个问题都多一次外部搜索——更贵、更慢，还可能答偏。工程上选便宜的那条路。

**第 8 节**：半句话的证据比没有更糟。截断会产生"看起来像证据、其实语义不完整"的文本，模型引用它就会答错。整条丢，至少不会污染判断。

## 附录 C：站点 9 为什么不在主链路

`reorder_service.py` 只服务 `POST /chat/reorder`（前端单独做文档重排），`AgenticRagService.run()` 里根本没有它。值得看的是它的失败处理：返回 `success: False` + 空列表，调用方按原顺序降级。凡是"锦上添花"的环节，都该长这样——挂了不影响主流程。

## 附录 D：读完后的面试口径（三句话）

1. 写入侧是生产者-消费者：切片丢线程池并行，写入串行，队列做背压；块带 `user_id` 标记，为检索隔离做准备。
2. 读取侧五步：规划 → 图/文并行检索（向量 + 全文 RRF 融合）→ 可答性评估 → 联网兜底 → 合并去重后 6000 字封顶。
3. 降级处处存在：planner 三层降级、图检索挂了文本照用、evaluator 挂了判可答、reorder 挂了按原序——每一处都是"失败时选便宜的那条路"。
