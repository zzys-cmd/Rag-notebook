## 0. 先定位：RAG 在你项目里到底是什么

一句话：**上传 → 切片 → 向量化 → 存 Neo4j → 两路召回 + RRF → 判断够不够 → 拼上下文 → 交给模型**。

模块 2484 行，是全项目最大的。但要分清三层，面试官会分别问：

| 层 | 你做了什么 | 会不会被问 |
|---|---|---|
| 数据层 | 切片、embedding、Neo4j 向量/全文索引 | 会，且必须答得出参数 |
| 检索层 | 向量 + 全文双路、RRF 融合、图谱检索 | 会，这是核心 |
| 决策层 | planner 规划、evaluator 判可答性、web 兜底 | 会，这是"Agentic"的部分 |

**注意**：面试官问 RAG 的方式和问 Agent 完全不同 —— Agent 偏工程（状态、并发、中断），RAG 偏**效果和数据**（召回准不准、参数为什么这么定、怎么评测）。

## 1. 六条追问链

### 链 1｜文档进来之后怎么处理

1. **上传一个 PDF 到能被检索到，中间发生了什么？**
   加载（PDF 走多模态解析，图片单独抽取）→ `RecursiveCharacterTextSplitter` 切片（1000 / 20）→ 入队 `graph_build_tasks` → worker 里算 embedding → 写 `(:Chunk)` 节点（含 embedding 属性）→ 建索引。
   位置：`document_handler/processor.py:174` → `graph_service.py` → `neo4j_graph_store.py:555`

2. **为什么 chunk_size 是 1000？**
   中文 1000 字约 700–900 token，能装下 2–3 个完整段落；再大单块语义太杂、召回精度下降；再小则上下文不完整、模型答不全。**上限来自 embedding 模型的输入限制，下限来自"一个块要能独立成意"。**

3. **overlap 为什么只有 20？**（→ 这是硬伤，见第 4 节）
   业界通常 10–20%，也就是 100–200 字。20 字在中文里基本等于"只重叠了一句话的尾巴"，跨块的信息会被切断（比如分页处的一句话被切成两半，两半都不完整）。

4. **分隔符的顺序有意义吗？**
   有。`["\n\n", "\n", "。", "！", "？", "!", "?", " ", ""]` 是从粗到细 —— 先按段落切，段落太大再按句号切，最后才退到按空格/字符强行切。这样能最大限度保住语义边界。

5. **表格和图片怎么办？**
   PDF 里的图片单独抽取存盘，chunk 上记 `image_paths`，前端通过 `/knowledge/image/{md5}/{img}` 访问（`vector_store.py:60-64`）。

### 链 2｜向量存哪里、怎么检索

1. **向量存在哪？为什么不用 Chroma / FAISS？**
   **存在 Neo4j 的 `(:Chunk)` 节点上**（`embedding` 属性），用 Neo4j 原生向量索引 `chunk_embedding_index`（cosine）。
   理由：一个库同时提供向量检索和关系遍历，省一套组件；而且 Chunk 天然要和 `(:Entity)` 连边（`MENTIONS`），拆到两个库反而要做跨库 join。

2. **向量索引的维度怎么定的？**
   **启动时探测**：`probe_embedding_dims(embed_model)` 实际算一次 embedding 拿到维度（`neo4j_client.py:147`）。
   换 embedding 模型时如果维度和已有索引不一致，会**直接 raise**（`:149-153`）—— 因为维度不同不能共存，必须清空重抽。

3. **检索为什么要两路？只有向量不行吗？**
   向量擅长语义相近（"怎么提高记忆力"能召回"记忆方法"），但**对专有名词、编号、代码标识符很弱**（"qwen3-max" 可能召回一堆无关的东西）。全文索引补这一块。两路是互补不是冗余。

4. **RRF 怎么算的？为什么用 60？**
   `1/(60 + rank)`，两路各取 `2×limit` 候选，按 chunk id 累加分数，取 top limit（`neo4j_graph_store.py:694-713`）。
   60 是 RRF 原论文的经验值（k 越大，排名靠前的差距越平缓）。好处是**不需要把两路分数归一化** —— 向量分是 cosine（0–1），全文分是 Lucene 的 BM25 分（没有上界），直接加权平均会被量纲毁掉。

5. **两路都召回同一个 chunk 会怎样？**
   分数会累加（两次 `rrf[id] +=`），排名更靠前 —— 这正是 RRF 想要的效果：**两路都认可的更可信**。

6. **全文检索的 query 直接丢进去就行吗？**
   不行。先 `_LUCENE_SPECIALS.sub(" ", query)` 清掉 Lucene 语法字符（`:699`）。不清的话用户输入 `a AND b`、`*`、`(` 会改变查询语义甚至报错。

7. **embedding 算不出来怎么办？**
   降级成纯全文检索。`_query_embedding` 失败返回 `None`（`local_retriever.py:142-152`），`search_chunks` 里 `if query_embedding:` 直接跳过向量那一路（`neo4j_graph_store.py:687`）。
   **说清这个降级是加分项**：检索不能因为 embedding 服务挂了就整个不可用。

### 链 3｜图谱检索是怎么加进来的

1. **为什么还要图谱检索？向量检索不够吗？**
   向量问的是"这段文字**像不像**问题"，图谱问的是"这段文字**提没提到**那个东西"。相似 ≠ 提到。
   典型场景：问"RAG 和知识图谱有什么关系"，向量能召回讲 RAG 的块，但不一定召回"这两个概念同时出现"的块；图谱先定位实体 RAG 和知识图谱，再拿它们共同被哪些 chunk 提到。

2. **但用户问的是一整句，怎么匹配实体？**
   `QueryEntityExtractor` 先用 LLM 从问句里抽实体候选词（`query_entity_extractor.py:78`），失败回落规则拆词 + 去噪词表（`:39-51`）。
   为什么必须抽：`search_entities` 是 `%...%` 模糊匹配，拿整句"DeepSeek 是什么"去匹配，几乎命中不了"DeepSeek"这个实体名。

3. **图谱检索返回的是什么？**
   两部分：实体本身的证据（描述 + 类型 + 别名 + 关联来源，`local_retriever.py:108-114`）+ 命中实体的 chunk 原文（`get_chunks_mentioning`，`neo4j_graph_store.py:729`）。
   第二部分是为了**让图谱证据有正文可引用**，否则只有一句实体描述，模型没法答。

4. **图谱检索拖慢速度了吗？**
   会 —— 它内部还有一次 LLM 调用来抽实体。所以 `service.py:73-85` 把图谱检索和文本检索**并行**跑（两个 `asyncio.create_task`），并且图谱那路失败不阻塞文本那路。

### 链 4｜planner 在规划什么

1. **为什么要有 planner？直接固定"向量 top5"不行吗？**
   不行，因为问题类型不同：闲聊不需要检索；问"是什么"适合图谱 + 混合检索；问"最新价格"需要联网。固定策略要么浪费（闲聊也检索），要么漏（只走一路）。
   位置：`planner.py:165`

2. **planner 输出什么？**
   `RetrievalPlan`：`need_retrieval`（要不要检索）、`steps`（每步带 `tool` / `query` / `top_k`）、`allow_web_fallback`、`reason`。工具枚举就四个：`search_notes` / `search_knowledge_base` / `hybrid_search` / `search_graph`。

3. **planner 挂了怎么办？**（这是三层降级，必答）
   1. LLM 纯文本返回 → 正则抓 JSON → pydantic 校验（`_text_plan`，`:187`）
   2. 文本解析失败 → `with_structured_output(RetrievalPlan, method="json_mode")`（`:210`）
   3. 都不行 → 规则 `_fallback_plan`（`:243`）：闲聊不检索 / 实体类问题走图谱+混合 / 其他走混合
   **关键**：两条 LLM 路径共享**一个 deadline**（`deadline = now + PLANNER_TIMEOUT_S`，`:170`），不是各给一份超时。所以最坏情况总耗时还是 ≤ 12 秒（.env 里配的）。

4. **为什么用 json_mode 而不是 function-calling？**
   代码注释写了：小模型做 tool-call 结构负担重，容易超时或乱写；纯 JSON + pydantic 校验是它的甜点区（`planner.py:213-214`）。

5. **planner 用的是哪个模型？为什么不用主模型？**（这题答好很加分）
   独立小模型（`.env` 里 `PLANNER_MODEL_NAME=qwen3.8-omni-flash`），不是主回答的 `deepseek-v4.1-flash`。
   **原因写在注释里**（`planner.py:114`）：早期复用主模型，"那（就）是 39 秒的来源"。规划只需要吐一个小 JSON，用大模型纯属浪费，而且大模型思考链会把首 token 拖到没法看。

6. **小模型乱来怎么办？**
   `_clamp`（`:234-241`）：步数强制截断到 2 步、`top_k` 限幅到 1–5。**这是防小模型发散的双保险**。

### 链 5｜证据够不够、不够怎么办

1. **evaluator 在判什么？**
   判断"本地证据能不能回答问题"，决定要不要走 web 兜底。位置：`evaluator.py:77`

2. **每次都调 LLM 吗？**
   不是，有两条规则快路径（不花钱）：
   - 没有证据 → 直接判不可答（`:79-86`）
   - query 含新鲜词（"最新/今天/价格/news"）→ 直接判不可答、需要联网（`:87-94`）
   其余才走 LLM 判相关性（`:124`）。

3. **为什么"有证据"不等于"可答"？**（这是这层存在的理由）
   向量检索**永远返回 top-k**，哪怕库里根本没相关内容 —— 它会拿最不相关的块凑数（比如你问一个笔记里没记过的人，它照样返回 5 条噪声）。
   所以必须再判一次"这些证据和问题**相关吗**"，否则模型会拿着无关资料硬答。

4. **LLM 判定失败怎么办？**
   回落成"有证据即视为可答"（`_rule_fallback`，`:111`）。方向是保守的：宁可让模型硬答一次，也不要无谓地卡住用户。

5. **web 兜底真的能用吗？**（→ 硬伤，见第 4 节）
   代码路径是通的（`service.py:158` → `web_search.py`），但 `.env` 里 `WEB_SEARCH_ENABLED=false`，实际**关着**。所以现在判"不可答"之后只是白跑一趟，拿回空结果。

### 链 6｜最后怎么拼给模型

1. **多个来源的证据怎么合并？**
   `merge_evidence`（`evidence.py:17`）：先按 `(source, id)` 去重，再按"内容规范化后相同"去重（`re.sub(r"\s+", " ", content).lower()`），最后截到 **8 条**。

2. **为什么还要按内容去重？**
   同一个 chunk 可能同时被向量检索和图谱检索拿到，id 一样会被第一道拦住；但**不同来源的 chunk 可能内容一模一样**（比如笔记里抄了一段文档），这就要靠内容去重。**两道去重防的是两种重复。**

3. **拼上下文时带什么？**
   `format_evidence_context`（`evidence.py:42`）：每条前面加 `[序号] 来源：知识库《标题》`，有 url 就加 URL，总长度限 **6000 字**。
   **为什么要带来源标注**：让模型能说"根据《XX》文档"，也方便你排查是哪个来源喂错了。

4. **8 条 / 6000 字够吗？**
   够，而且是有意的：太少答不全，太多模型会迷失（中间位置的证据最容易被忽略）。8 条 × 平均 750 字 ≈ 6000，正好卡住。

## 3. 会被追问的"标准答案"型问题

这些是面试官拿来对照业界做法的，你项目里**没做或做得不一样**，必须提前想好说法。

### Q1 你用了 rerank 吗

**实话**：有 `ReorderService`（`reorder_service.py`，调云端 rerank API，兼容 SiliconFlow / Jina / Cohere 协议），但**只挂在独立的 `/chat/reorder` 接口上**（`chat_service.py:48`），**没接进 Agentic RAG 主链路**。而且 `.env` 里 `RERANKER_*` 全是注释状态。

**怎么答**：承认没接，然后说清为什么不接也行 —— RRF 已经做了两路融合，向量和全文的排序质量在笔记+文档这个量级上够用；接 rerank 会让每轮多一次 300ms 以上的 API 调用，而收益在 top-8 里不明显。
**加分**：补一句"如果要做，正确位置是在 RRF 之后、evaluator 之前，对 top-8 做跨编码器精排"。

### Q2 为什么不做过 query 改写 / HyDE

**答**：planner 已经承担了一部分 query 改写的职能 —— 它会把一个问题拆成最多 2 个检索步，每步可以带不同的 tool 和 query。这比固定模板的改写更灵活。没做 HyDE（假设性文档嵌入），是因为它要多一次 LLM 生成 + 一次额外检索，延迟翻倍，而我的场景是个人笔记，query 和文档的表达差异没那么大。

### Q3 召回率多少？怎么测的

**这是最容易被问穿的一题，不要编数字。**

**答**：有离线评测脚本（`scripts/eval_recall.py`、`eval_graph_entity_recall.py`、`eval_graph_multihop.py`），但没有持续维护的标注集，所以给不出可靠的 recall@k。
**能说的**：可以说清楚"如果要做，我会怎么测" —— 构造 50–100 条 (query, 正确 chunk id) 对，算 recall@5 / MRR；分三档难度（字面命中 / 同义改写 / 需要多跳）。

### Q4 怎么防幻觉

**答**（按四层说，每层都能指到代码）：
1. 检索层：双路召回 + RRF，尽量让相关证据进 top-8
2. 装配层：`format_evidence_context` 强制带来源标注（`[1] 来源：知识库《XX》`），模型有据可引
3. 判定层：evaluator 判证据相关性，不够就判不可答
4. 提示层：prompt 里要求基于给定资料回答（`rag_context_prompt`）
**诚实补一句**：没有做引用校验（回答里的句子回查证据），这是可以加强的点。

### Q5 为什么用 Neo4j 做向量库，不用专业向量库

**答**：规模。个人笔记 + 文档，chunk 数在万级，Neo4j 的 HNSW 索引完全够；专业向量库（Milvus/Qdrant）的优势在千万级以上和更丰富的过滤，我这里用不上，反而多一套运维。
**加分**：真正的理由是 **chunk 要和实体连边** —— `(:Chunk)-[:MENTIONS]->(:Entity)`。向量库做不了这个，要跨库 join。

### Q6 用户隔离怎么做的

**三层，缺一不可**：
1. 向量/全文检索：`WHERE node.user_id = $uid`（`neo4j_graph_store.py:690/703`）
2. 取节点回填：`MATCH (c:Chunk) WHERE c.id IN $ids AND c.user_id = $uid`（`:716`）—— **注释专门写了"id 跨用户可重复（文档 md5 相同），必须叠加 user_id 过滤防串用户"**
3. 图谱：`WHERE e.user_id=$uid AND ... c.user_id=$uid`（`:738`）

**这题一定要讲第 2 条**：因为 chunk id 是 `{kind}:{md5}:{index}` 拼的，两个用户传同一个文件会拿到相同 id，只按 id 取节点就会串。

## 6. 一句话总结这个 RAG 的水平

如果面试官问"你觉得这套 RAG 做得怎么样"，标准答法是**分层评价**，不要自夸也不要全否：

> 检索层的工程完成度可以 —— 双路 + RRF + 降级链 + 用户隔离都想到了，还额外做了图谱检索这条路。
