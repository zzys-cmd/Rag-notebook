# 面试题库：RAG + Agent + 知识图谱

> 全部答案对着 `backend/` 当前源码写的，数字来自 `backend/results/` 里的真实评测报告。
> 标【必答】的是几乎一定被问、且答不好会直接掉分的；【加分】是能拉开差距的；【陷阱】是答错等于自曝没读懂的。

## 使用说明

**答题三段式**（每题都按这个顺序说，30～60 秒）：
1. 我做了什么（一句话结论）
2. 为什么这么做（对比另一种做法）
3. 代价是什么 / 我为此加了什么兜底

第 3 段最重要。只讲 1、2 段听起来像背文档，讲得出 3 段才像作者。

**必背 10 题**（其余可以现编，这 10 题必须张口就来）：
1. 用一分钟介绍这个项目
2. 一次提问从请求到返回，中间发生了什么
3. 前置 RAG 和 Agent 里的 search_rag 为什么不是重复
4. 混合检索怎么做的，RRF 的 k 为什么是 60
5. planner 为什么要单独用一个小模型
6. 人工审批（HITL）怎么实现的，中断现场存在哪
7. 图谱抽取的任务队列怎么保证不重复、不覆盖
8. 删除一个文档，图谱里的实体怎么清
9. 这个项目最大的瓶颈是什么（延迟），你做了哪些优化
10. 如果重做，你会改什么

# 第一部分 开场

## Q1【必答】用一分钟介绍一下这个项目

个人知识管理和问答系统。用户可以把 PDF、Word、PPT、Markdown 传到知识库，也可以自己写笔记，然后对这些内容做检索问答。

后端 FastAPI，存储是 MySQL + Neo4j + Redis。三块核心：

- **RAG**：文档切片后，向量和全文索引都落在 Neo4j 的 Chunk 节点上，检索走混合召回 + RRF 融合，前面加了一个 planner 决定要不要检索、检索几步，检索完由 evaluator 判本地证据够不够，不够就走外部搜索兜底。
- **Agent**：LangChain 1.0 的 create_agent 编了 9 个工具（笔记增删查、统计、复习、RAG 二次检索、时间、用户信息），带人工审批中间件，写操作要用户点确认才执行。
- **知识图谱**：后台 worker 消费任务表，用 LLM 从笔记和文档里抽实体和关系写进 Neo4j，检索时作为独立的一路证据。

**追问：你自己负责哪部分？**
全部。从表结构到检索参数到评测脚本都是我一个人写的，所以每一条取舍我都能说清原因，也说得出它现在的短板。

## Q2【必答】一次提问，从请求到返回中间发生了什么

前端 POST `/chat/agent/query/stream`。后端分两段：

**第一段，前置 RAG 管线**（`AgenticRagService.run`）：
1. planner 用小模型判断要不要检索、拆成几步。8 秒超时，出不来就降级成规则计划。
2. 如果计划里同时有图谱步骤和文本步骤，两路用 `asyncio.create_task` 并行跑。
3. evaluator 判本地证据能不能回答问题。判不能，或者问句里带"最新/今天/价格"这类新鲜词，就走外部搜索。
4. 证据去重，拼成不超过 6000 字的上下文。

**第二段，Agent**：
把上面那段上下文塞进 system prompt，Agent 流式跑。模型如果觉得资料不够，可以调 `search_rag` 再检索，单请求最多两次。生成过程通过 SSE 逐块推给前端，结束后往 `chat_messages` 落一条镜像。

**两段的连接点**是 `rag_context` 这个字符串，以及 `rag_searched_queries`——前置管线检索过哪些 query 会传给 Agent，让 `search_rag` 的护栏知道哪些角度已经覆盖了，不重复检索。

## Q3【陷阱】你说的"上下文"具体是怎么拼的，有没有长度控制

`format_evidence_context` 做的，两条硬限制：

- 证据条数：`merge_evidence` 上限 8 条。去重做了两层——`(source, id)` 重复的直接丢；正文做空白归一化 + 小写后相同的也丢（同一个 chunk 从图谱和文本两路都召回的情况）。
- 总字数：6000 字。逐条累加，一旦"已用 + 下一条"超过 6000 就 `break`，**不是截断**——宁可少一条完整证据，不要一条被切一半的。

每条证据带来源标签（笔记 / 知识库 / 知识图谱 / 外部搜索）和标题，外部搜索额外带 URL。这样模型回答时能说清引用的是哪一份材料。

代价是：如果排在前面的证据都很长，后面的就进不去了。现在的排序是按检索分数，没有做"长度感知的装箱"。

# 第二部分 RAG 模块

## Q4【必答】完整讲一下检索链路

1. planner 出计划，`RetrievalStep` 列表，每步有 `tool` 和 `top_k`。
2. `LocalRetriever.search` 按 `tool` 分派：`search_notes` 只搜 note 类 Chunk，`search_knowledge_base` 只搜 doc 类，`hybrid_search` 两类都搜，`search_graph` 走实体检索。
3. Chunk 检索在 `Neo4jGraphStore.search_chunks` 里：query 算 embedding，向量索引和全文索引各取 `2 × limit` 个候选，应用层算 RRF 融合分，取 top limit。
4. 单步失败不阻塞其余步骤——`LocalRetriever` 里每个 step 都包了 try/except，Neo4j 挂了就记 warning 跳过，返回剩下的。
5. 结果转成 `Evidence`，交给 evaluator 和 `merge_evidence`。

**关键设计**：检索原语只有"Chunk 检索"和"实体检索"两种，笔记和文档在存储层就统一成 Chunk 了，所以在检索层不用区分两套逻辑。

## Q5【必答】切片怎么做的，chunk_size 1000 和 overlap 20 怎么定的

`RecursiveCharacterTextSplitter`，参数在 `app/config/document.yaml`：`chunk_size: 1000`、`chunk_overlap: 20`。

分隔符按优先级降级：`\n\n`（段落）→ `\n`（换行）→ `。！？!?`（句末）→ `空格` → 空字符串（逐字硬切）。

- 1000 是字符数不是 token。中文 1000 字大概 700 上下 token，跟常见 embedding 模型的窗口比是保守的，留了余量。
- overlap 只给了 20，很小。原因是分隔符列表里已经有句末标点，切点基本落在句子边界上，不需要大 overlap 来补上下文；overlap 大了反而让相邻 chunk 高度重复，混合检索时同一个内容占满候选池。

**这里有个坑我要主动说**：`AsyncTextSplitter` 里还写了一个 `_optimize_chunks`，用 embedding 算相邻 chunk 余弦相似度，超过 0.7 就合并，本意是"语义完整再切"。但它只挂在 `split_text` 上，文档和笔记走的是 `split_documents`，实际没生效。所以现在线上就是纯递归字符切分，那段是死代码。要么补上，要么删掉——我倾向于删，因为两两算 embedding 会让上传慢一个数量级，收益不明。

## Q6【必答】混合检索怎么做的，RRF 为什么 k=60

`search_chunks` 里：

```
向量路：CALL db.index.vector.queryNodes('chunk_embedding_index', 2*limit, $embedding)
全文路：CALL db.index.fulltext.queryNodes('chunk_text_index', $q)  → LIMIT 2*limit
融合：  score = Σ 1 / (60 + rank)     # rank 从 1 开始
```

- 两路各取 `2 × limit` 做候选池，各自按名次打分，同一个 id 相加，最后排序取 top limit。
- k=60 是 RRF 原论文的经验值。它的作用是**压平头部差异**：rank 1 和 rank 2 的分差是 `1/61 - 1/62 ≈ 0.00026`，很小。如果不加 k 或者 k 很小，某一路排第一的文档会一票决定结果，另一路的判断等于白做。加了 60 之后，两路都排前面的文档才会明显胜出。
- 返回的 `score` 是融合分，两路的原始分数（`vector_score` / `fulltext_score`）放在 `metadata` 里，前端展示用。因为融合分本身没有"相似度"含义，不能拿去跟阈值比。

**为什么两路都放 Neo4j**：Chunk 本来就要进图谱（要做 chunk 级 MENTIONS 指向实体），放一个库里，向量召回、全文召回、图扩展能在一次会话里完成，不用跨库拼，也少一个组件要运维。代价是规模上不如专用向量库，百万级 chunk 以上要重新评估。

## Q7【加分】query 向量化失败会怎么样

退化，不是报错。`_query_embedding` 里 `embed_model` 为 None 或者 embed 抛异常，都返回 `None`；`search_chunks` 拿到 `None` 就跳过向量那一路，只走全文，RRF 里也只有一路的分。

同理全文那一路：query 里的 Lucene 特殊字符（`_LUCENE_SPECIALS`）会先被替换成空格，清理完如果是空串就跳过。

两路都没结果就直接返回空列表，上层 `LocalRetriever` 收到空 evidence，evaluator 的规则快路径判"不可答"，触发外部搜索。整条链路没有一处因为单点失败抛出去。

## Q8【必答】planner 为什么要单独用一个小模型

因为用主回答大模型做规划，实测能到 39 秒。

`_resolve_planner_chat_model` 的注释里写了这一条：不再复用 `init_manager.chat_model`。规划是个很轻的任务——输入一个问句，输出一个 JSON（要不要检索、几步、每步用什么工具、top_k 多少），不需要大模型的推理能力。换成配置独立的小模型（`PLANNER_*` 环境变量，没配就复用 embedding 通道的配置，再没有才回落主模型）之后，这一步降到 2～4 秒。

另外做了单例缓存 `_planner_model_cache`，避免每个请求都新建 client 丢掉 HTTP keep-alive。

**追问：小模型规划不准怎么办？**
三层降级（见下一题），而且 `_clamp` 会兜住小模型发散：步数封顶 2 步，每步 `top_k` 夹在 1～5。小模型爱拆成七八步、top_k 给 20，这些都会把延迟放大，所以在结构上直接夹死，不指望它自觉。

## Q9【必答】planner 的三层降级是什么

`AgenticRagPlanner.plan`：

1. **文本 JSON 解析**：prompt 里给 few-shot，让模型直接吐 JSON，`_extract_json_object` 剥掉 ```json 围栏、再用正则抓第一个 `{...}`，然后 `RetrievalPlan.model_validate` 校验。这是主路径。
2. **pydantic 结构化输出**：文本这条路失败（超时、返回非文本、JSON 解析不出来）才走。用 `with_structured_output(..., method="json_mode")` 而不是 function-calling——注释里写了原因：小模型做 tool-call 结构负担重，容易超时或乱写，纯 JSON 加 pydantic 校验是它的甜点区。
3. **规则兜底**：模型完全不可用。`_fallback_plan` 三个分支——纯寒暄（hi / 你好）不检索；问句里含"关系 / 关联 / 实体 / 是什么 / who is"等词，走图谱 + 混合检索两步；其余走一步混合检索。`allow_web_fallback` 看问句里有没有新鲜词。

**总预算制**：8 秒的 deadline 是两条路共用的，不是各 8 秒。文本路径用光时间，结构化路径剩余时间不足 0.5 秒就跳过，直接规则兜底。所以最坏情况整体仍然 ≤ 8 秒。

## Q10【必答】为什么要做"可答性评估"，多此一举吗

不多余，因为向量检索**恒返回 top-k**。

用户问一个知识库里根本没收录的人名，向量检索照样会返回 5 条"最像"的切片，全是噪声。如果直接把这些拼进上下文，模型要么硬编，要么说"根据资料无法回答"——但它其实是被噪声误导的，不是资料真的没有。

`AnswerabilityEvaluator.evaluate` 三步：

1. 规则快路径，不调 LLM：没证据 → 直接判不可答；问句带新鲜词（最新/今天/价格/版本/news 等）→ 直接判不可答，需要联网。
2. LLM 判相关性：拿最多 8 条证据、每条截 300 字，让模型判"这些证据能不能回答问题"，顺便给出 `web_queries`。
3. LLM 失败或不可用 → `_rule_fallback`，有证据就当可答（置信 0.75）。**这一层是故意的保守**：宁可答得不全，也不要因为评估器挂了就把所有问题都丢去搜网。

## Q11【加分】什么时候会走外部搜索，planner 的 allow_web_fallback 为什么没用上

`_maybe_search_web` 的触发条件是：`answerable=False` **或者** evaluator 显式给了 `web_queries`。

planner 出的 `allow_web_fallback` 只作为规划提示，不再一票否决。代码注释里写了原因：本地知识缺口有两种——一种问的是时效性内容，另一种是"检索回来的东西跟问题不相关"，后一种 planner 在规划阶段看不出来，只有检索完才知道。所以硬开关收敛到 `WebSearchClient` 自己（开关、provider、key 三处配置）。

这个改动是我踩了坑之后改的：一开始让 planner 说了算，结果问"我笔记里提到的那个人是谁"，planner 觉得不需要搜网，检索回来一堆噪声，模型只能硬答。

## Q12【加分】检索效果怎么评估的，有数字吗

有，`backend/scripts/eval_recall.py`，数据集用 MTEB 的 DuRetrieval（500 个 query，2 万篇文档，切成 21359 个 chunk），走的是线上同一套 `search_chunks`，文档级去重后对齐 qrels 算标准 IR 指标：

| 指标 | 值 |
|---|---|
| recall@5 | 0.7207 |
| recall@10 | 0.8646 |
| hit@5 | 0.9580 |
| MRR | 0.9384 |
| nDCG@10 | 0.8636 |
| MAP | 0.8192 |
| 延迟 p50 / p95 | 259.6 / 321.1 ms |

另外还有三个脚本：`eval_end2end.py`（自动合成 QA，LLM 裁判打忠实度和正确性，忠实度 4.35 / 正确性 3.75）、`eval_graph_entity.py`（实体检索 hit@1 = 0.90）、`eval_graph_multihop.py`（多跳对比，见 Q24）。

**为什么 recall@1 只有 0.2697 但 MRR 有 0.9384**：recall@1 的分母是"该 query 的相关文档总数"，一个问题常常有 4～9 篇相关文档，top-1 只能装下一篇，所以 recall@1 天然上不去。MRR 只看第一条相关文档排第几，0.9384 说明首位基本就是相关的。这两个指标要一起看，单看 recall@1 会误判。

## Q13【陷阱】召回不准，你怎么排查

分四层，从便宜的往下查：

1. **先看是"没召回"还是"没排上"**。`search_chunks` 返回的 `metadata` 里有 `vector_score` 和 `fulltext_score`，如果某条相关文档在候选池里但排到 limit 之外，是排序问题；候选池里压根没有，是召回问题。这一步决定了后面查哪里。
2. **召回问题先怀疑分词**。全文那一路是 Neo4j 的 Lucene 索引，中文分词器配错的话，"知识图谱"会被切成单字，召回质量断崖。向量那一路则怀疑 embedding 模型是不是中文语料训的。
3. **切片问题**。答案被切在两个 chunk 中间，两半都不完整，谁都召不回。这就是 overlap 的作用，我现在只给 20，如果发现这类 case 多，先调 overlap 而不是换模型。
4. **多路结果打架**。图文两路各有各的判断，RRF 融合后可能把真正相关的压下去。调 k 值或者给两路加权。

# 第三部分 Agent 模块

## Q14【必答】为什么用 create_agent，不自己写 ReAct 循环

三件事我不想自己写：工具调用的消息协议（AIMessage.tool_calls 和 ToolMessage 的配对）、中断恢复（checkpoint 的序列化和重放）、以及中间件的挂载点。

`create_agent` 是 LangChain 1.0 的入口，返回的是一个编译好的 LangGraph `CompiledStateGraph`，不是老的 `AgentExecutor`。这个区别要分清：

- `AgentExecutor` 是 langchain 0.x 的东西，靠 `max_iterations` 卡轮数，靠 `handle_parsing_errors` 兜解析错误，已经被弃用了。
- `create_agent` 没有这两个参数。所以轮数控制要换成 `ToolCallLimitMiddleware`，解析错误要由编排层 try/except 兜。`agent.py` 里专门写了一行注释说明这件事，因为照着老教程抄会找不到参数。

**追问：那为什么不直接用 LangGraph 手搭图？**
手搭要自己定义 State、自己连 model 节点和 tools 节点、自己写条件边。create_agent 就是这套东西的封装，我只需要给模型、工具、prompt、中间件。除非要做很特殊的拓扑（比如多 agent 互相调用），否则没必要自己搭。

---

## Q15【必答】工具怎么定义的，user_id 为什么不在参数里

`@tool(description=...)` 装饰 async 函数，description 是给模型看的，决定它什么时候调这个工具。

9 个工具：`what_time_is_now`、`get_user_info_tools`、`search_notes_tool`、`get_note_stats_tool`、`get_today_reviews_tool`、`mark_reviewed_tool`、`create_note_tool`、`get_related_notes_tool`、`search_rag`。

**user_id 绝不放工具参数**。工具参数是模型填的，把 user_id 暴露成参数等于让模型决定查谁的数据——prompt 里一句话就能让它填别人的 id。做法是用 `ContextVar`：

```python
current_user_id_var: ContextVar[str] = ContextVar('current_user_id', default=None)
```

run 开始时 `set_current_user_id(user_id)`，工具里 `get_current_user_id_from_context()` 取。ContextVar 跟着 asyncio task 走，同一个请求里的所有工具调用拿到的是同一个值，并发请求之间不会串。

**追问：工具里取不到 user_id 怎么办？**
返回"错误: 无法确定用户身份"，不是抛异常。抛异常会让整个 run 挂掉，返回字符串模型能看懂，会告诉用户"我现在没法确认你的身份"。

## Q16【必答】人工审批（HITL）是怎么实现的

四个环节：

1. **白名单**：`DEFAULT_APPROVAL_TOOLS` 里只放了 `create_note_tool`，`allowed_decisions` 是 `["approve", "reject"]`，还挂了个 `description` 回调 `_describe_create_note`——把标题、正文字数、前 120 字预览生成审批摘要。**不能把全文塞进审批负载**，一篇长笔记会把 interrupt 的 payload 撑得很大。
2. **拦截**：`HumanInTheLoopMiddleware` 挂在中间件链尾，模型决定调这个工具时，在图里 interrupt，run 停住，状态写进 checkpoint。
3. **通知**：`_emit_agent_events` 结束后 `aget_state` 查 `interrupts`，有负载就发一个 `{"type": "interrupt", "run_id": ..., "payload": ...}` 的 SSE 帧，同时把 run_id 写进会话的 `pending_run_id`。
4. **恢复**：前端 POST `/chat/agent/resume`。后端**从会话里读 pending_run_id，不信客户端传的**——客户端能指定 thread_id 就能恢复别人的 run，那是越权。然后用 `Command(resume={"decisions": [...]})` 在同一个 thread 上继续。

**几个边界都处理了**：
- 恢复前先查 `pending_writes`，没有 `__interrupt__` 说明这个 run 已经审批完了，返回 `ALREADY_COMPLETED`，不重复执行工具、不重复落镜像。
- 恢复出错时**不删 thread、不清 pending**，留着重试。
- 会话里已有 pending 且那个 run 还在等审批时，拒绝新问题（`PENDING_EXISTS`），否则两个 run 抢一个会话。
- 已经审批完的历史 thread 会被保留（给前端查审批前快照），等下次中断时把上一个删掉，避免无索引的孤儿越积越多。

## Q17【必答】中断现场存在哪，为什么不能存内存

存在 MySQL 的 `agent_checkpoints` 和 `agent_checkpoint_writes` 两张表里，走我自己写的 `MySQLCheckpointSaver`。

存内存不行，因为审批是**人的动作**，人可能十分钟后才点。这期间进程重启、或者请求被负载均衡打到另一个 worker，内存里的现场就没了，用户点"同意"直接 500。落库之后，`run_id` 就是个持久句柄，谁来恢复都行。

**追问：为什么自己写，不用官方的？**
官方只提供 SQLite 和 Postgres 的 saver，我用的是 MySQL。接口不复杂，`BaseCheckpointSaver` 要实现五个方法：`aget_tuple` / `alist` / `aput` / `aput_writes` / `adelete_thread`。两个坑：

- upsert 语法要按方言分支。MySQL 是 `ON DUPLICATE KEY UPDATE` / `INSERT IGNORE`，SQLite 是 `INSERT OR REPLACE` / `INSERT OR IGNORE`。方言在第一次使用时探测一次然后缓存，不每次查。
- SQL 一律用 SQLAlchemy `text()` 的 `:name` 命名绑定，让引擎按方言编译成 `%s` 或 `?`。手写占位符会在换库时炸。

序列化用官方的 `JsonPlusSerializer`（`self.serde`），它能编码 `BaseMessage`，不用自己处理。

## Q18【陷阱】你有 checkpointer，多轮对话是怎么存的

**没用 checkpointer 存多轮**，这是刻意的。

每次 run 用一个全新的 `thread_id`（uuid），正常跑完就 `adelete_thread` 删掉。多轮历史在 MySQL 的 `chat_sessions` / `chat_messages` 里，每轮读出来，用 `_build_chat_history` 重建成 `HumanMessage` / `AIMessage` 对，拼在 `messages` 最前面。

这么分的理由：checkpointer 只负责"这一次 run 的中断恢复"，职责单一。如果把多轮也交给它，历史会越滚越长，每个 checkpoint 都要存全量 messages，表会迅速膨胀，而且这些数据跟会话列表是重复的——会话历史我已经有一份了。

**代价**：每轮都要重传一次历史，长会话 token 涨得快，现在没做摘要压缩。要加的话，是在 `_build_chat_history` 里对超过 N 轮的历史先过一遍摘要模型。

## Q19【必答】前置 RAG 和 Agent 里的 search_rag，不是重复吗

不重复，职责不同。

- **前置管线**：每轮必跑，用户能看见进度（"正在规划检索策略…"），跑完把 context 塞进 system prompt。它是确定性的，不依赖模型判断。
- **search_rag**：模型自己判断"现有资料不够、要换个角度再看"时才调。不是每轮都发生。

**为什么要两条**：如果只留前置，模型发现资料不够也没有补救手段，只能硬答；如果只留 Agent 自主检索，第一轮就要等模型想清楚要搜什么，首 token 更慢，而且用户看不到进度。

**护栏防的就是"两条变成重复"**：`MAX_RAG_CALLS = 2` 限制单请求真实检索次数；`normalize_query` 把 query 去掉空白、全半角标点、转小写之后比对，"什么是 RRF" 和 "什么是RRF?" 会被判成同一个角度，直接返回提示让模型换角度。前置检索过的 query 也会通过 `build_pre_searched_queries` 预置进 `searched` 集合，所以 Agent 不会把前置刚搜过的再搜一遍。

**现在的局限**：只做了字符归一化后的精确匹配，语义重复拦不住——"RRF 怎么算" 和 "RRF 公式是什么" 会被当成两个角度。要完善得上 embedding 相似度或者让模型判断。

## Q20【必答】流式是怎么实现的

`astream_events(version="v2")`，只处理四类事件：

| 事件 | 处理 |
|---|---|
| `on_chat_model_stream` | 取 chunk 文本，推进队列 |
| `on_tool_start` / `on_tool_end` | 推 `thinking` 事件，前端显示"正在调用 xxx" |
| `on_chat_model_end` | 兜底：非流式模型不产生 stream 事件，`full_response` 为空时从终态消息收一次 |

**两个坑**：

1. `on_chat_model_stream` 里必须 `if getattr(chunk, "tool_call_chunks", None): continue`。模型决定调工具时，流出来的 chunk 里有工具名和参数的 JSON 片段，不跳过的话用户会看到 `{"query": "RRF"...}` 这种原始参数混在回答里。
2. Agent 任务和 SSE 生成器要解耦。做法是 `asyncio.create_task(run_agent())`，agent 往 `asyncio.Queue` 塞事件，生成器用 `asyncio.wait_for(queue.get(), timeout=0.1)` 轮询，`agent_done` 事件置位后**先把队列排空**再发 `done` 帧——不排空的话最后几个 token 会丢。

`on_chat_model_stream` 里还顺手记了首 token 耗时，日志里能直接看到 `first_token=xxx ms`，调延迟的时候靠这个定位是模型慢还是前面慢。

## Q21【必答】怎么防工具死循环

三层，从外到内：

1. `ToolCallLimitMiddleware(run_limit=5)`——单轮 run 最多 5 次工具调用，超了直接停。这是替代老 `AgentExecutor.max_iterations` 的东西。
2. `ModelRetryMiddleware(max_retries=2)` + `ToolRetryMiddleware(max_retries=1)`——模型和工具失败都重试，但有上限。工具重试只给 1 次，因为工具大多是数据库操作，重试多了容易放大副作用。
3. `search_rag` 自己的请求级护栏 `MAX_RAG_CALLS = 2`——即使前两层没拦住，最贵的那个工具（会跑一整条 RAG 管线）最多两次。

**中间件是有序的**：6 个自定义钩子（`before_agent` / `after_agent` / `before_model` / `after_model` / `wrap_model_call` / `wrap_tool_call`）在前，3 个官方健壮性中间件在后，HITL 在最尾。顺序有意义——观测要在最外层包住所有调用，审批要在最内层贴着执行。

## Q22【加分】中间件写了些什么

6 个钩子分两类：

- **纯观测**（`before/after_agent`、`before/after_model`）：只打日志，而且**打摘要不打全文**——`_messages_summary` 输出"几条消息 + 角色序列 + 总字符数"。把 messages 全打进日志会让日志爆掉，而且里面是用户内容。
- **包装调用**（`wrap_model_call`、`wrap_tool_call`）：计时、提 token 用量（`usage_metadata`）、慢调用告警（超 5 秒）、工具参数截断到 200 字符再打日志。`model_call_hook` 还会通过 `thinking_callback` contextvar 往前端推一条 `model_metrics` 事件，前端能展示"这次模型调用花了多久、多少 token"。

**这里有个 contextvar 的用法值得说**：工具函数、中间件、`agent.py` 里的 emit 三处都要往前端推思考事件，但它们的调用栈没有共同的参数可以传。用 `thinking_callback_var` 这个 ContextVar 让三处都能拿到同一个回调，不需要层层透传。

## Q23【陷阱】同一个会话并发两个请求会怎样

会打架，所以我加了锁。

不打的话：两个 run 各自写 `pending_run_id`，后写的覆盖先写的；两个 thread 的 checkpoint 交错；前端收到两组 SSE 帧分不清是哪一轮的。

`_get_session_lock(user_id, session_id)` 返回一把 `asyncio.Lock`，`run` 和 `resume` 都 `async with` 这把锁，整个流式过程持锁。键里带 `user_id` 是因为 `session_id` 虽然全局唯一，但带上是防御——万一有会话 id 撞了，也不会跨用户串。

**局限我要说清楚**：这是进程内锁。多 worker 部署时，两个请求可能落到不同进程，锁就不起作用了，得换成 Redis 分布式锁或者数据库行锁。现在单进程 uvicorn，够用。

# 第四部分 知识图谱模块

## Q24【必答】有了 RAG，为什么还要知识图谱，它到底解决了什么

先把边界说清，避免误解：**现在 `search_graph` 做的是"从问句抽实体 → 匹配实体节点 → 返回实体描述 + 这个实体被提到的 chunk"，不是关系邻居的多跳扩展。**

它解决的问题是：问"XX 是什么、跟哪些东西有关"这类**实体型问题**时，纯 chunk 检索只能返回"包含这个词的段落"，拿不到这个实体本身的结构化信息——它的类型、别名、描述、被哪些来源提到过。这些信息在图里是节点属性，一次点查就有。

**关系数据存了但检索端还没用上**。我做过对比评测（`eval_graph_multihop.py`，15 条从图里真实 2 跳路径生成的问题）：

| 指标 | 图检索 | 纯文本 |
|---|---|---|
| 两端实体命中 | 0.933 | — |
| 证据含中间实体 | 0.867 | 0.600 |
| 端到端答案正确率 | 0.400 | 0.400 |

图路径在**证据覆盖**上确实高 26 个百分点，但**答案正确率没有增量**。原因就是上面说的：证据里"有"中间实体，和生成时"用得上"是两回事——我没做邻居扩展，模型拿到的还是几段文本，关系三元组没进上下文。

这个结论我写进了报告。它比"图检索效果很好"有用，因为它明确告诉我下一步该改哪里。

## Q25【必答】抽取链路完整讲一遍

worker 认领任务后，`process_task` 先做哈希判重，然后调 `_run_extraction`，八步（代码里编号到 7）：

1. **双链解析**（仅笔记）：`parse_links(body)` 抽 `[[标题]]`，纯字符串解析，不花 LLM。
2. **LLM 抽取**：`extract_entities` 给模型标题 + 正文前 6000 字，要它返回 `{entities: [...], relations: [...]}`。实体带 name / aliases / description / type / mentions，关系带 source / target / relation_type。
3. **来源存在性复检**：LLM 抽取要几秒到几十秒，这期间用户可能已经把笔记删了。落库前查一次源还在不在，不在就清掉 pending 日志直接返回，**不能让已删除的数据被"复活"**。
4. **认领复检**：`claim_check` 再验一次令牌（见 Q27），这是写图谱前的最后一道闸。
5. **实体 upsert + 关系先清后写**：`upsert_entity` 按 (name, user_id) MERGE；关系按 `source_id` + `source_type` 溯源，先删这个来源此前建的边再插新的，重抽不会翻倍，手动加的关系不受影响。
6. **来源级 MENTIONS**：先清后插，同一个事务里删旧的建新的，防中途失败留半套关联。
7. **Chunk 写入 + chunk 级 MENTIONS**：见 Q26。写完后做**引用收缩**——本轮没再关联的旧实体，从 `source_note_ids` 里摘掉，摘完没有任何引用也没人 MENTIONS 的，级联删除。
8. **双链边 + 落日志 + 推事件**：写 `graph_extract_logs` 置 success，通过 `event_bus` 推 `extract_done`，前端列表状态从"解析中"变成完成。

## Q26【加分】chunk 级 MENTIONS 是 LLM 建的还是规则建的

**规则建的，零 LLM 成本**。

`match_entities_in_chunks` 拿本轮抽出的实体名（含别名），在各个 chunk 文本里做字符串匹配，得到"实体 → 命中它的 chunk 序号列表"，然后 `set_chunk_mentions` 批量写 `(:Chunk)-[:MENTIONS]->(:Entity)`。

这么做的原因：实体和 chunk 的对应关系是纯机械的"这个词出现在这段文字里"，让 LLM 再判一遍是浪费钱和时间，还更容易出错。LLM 只用来做它擅长的事——从自由文本里认出"哪些是实体、它们之间什么关系"。

**Chunk 的 id 是 `{source_type}:{source_id}:{chunk_index}`**，文档的 `source_id` 是内容 md5。写入用 `MERGE (c:Chunk {id, user_id})`，复合键——因为两个用户传同一个文件 md5 一样，只用 id 做键会互相覆盖。后面所有查 Chunk 的地方也都带 `user_id` 过滤，同一个原因。

## Q27【必答】为什么用 MySQL 表当任务队列，不用 Celery

判断标准是任务特征和运维成本。

抽取任务是：低频（用户保存笔记才触发）、耗时（LLM 几秒到几十秒）、不需要精确调度。这种量级下，一个进程内 asyncio 循环每 2 秒轮询一张表完全够用，引入 broker + worker 服务是给自己找事。

**用表还有三个额外好处**：
1. 任务状态直接在 MySQL 里，前端查"这篇笔记解析到哪一步了"就是一次普通 query，不用再跟队列同步状态。
2. 进程重启后 pending 任务自动接着跑——worker 启动时 `recover_stale_tasks` 把上次遗留的 running 拨回 pending。内存队列做不到这点，重启就丢。
3. 任务和业务数据在同一个库，可以用同一个事务边界做"入队 + 改业务状态"。

**代价**：只能单实例。两个 worker 会互相抢，锁机制就是为此设计的（下一题）。要多实例得先引入 lease/owner，代码注释里写了这一条。

## Q28【必答】乐观认领 + run_token 具体解决什么

**认领**：先 `select` 一条 pending 按 `created_at` 排序，再

```sql
UPDATE graph_build_tasks SET status='running', run_token=?
WHERE id=? AND status='pending'
```

`rowcount = 0` 说明这瞬间被别人抢走了，返回 None 继续下一轮。这是乐观锁，不 `SELECT FOR UPDATE`，因为单实例下抢的概率很低，为它加行锁不值得。

**run_token 解决的不是并发抢，是"执行中被重新入队"**：

用户在笔记保存后马上又编辑保存了一次，`_enqueue_build_task` 会把同一行（`(user_id, source_type, source_id)` 唯一）覆盖成 pending 并写新令牌。此时老执行方还在跑 LLM 抽取，手里是旧正文。如果不拦，它一分钟后跑完会把**旧正文的抽取结果**写进图谱，覆盖掉新任务的成果。

所以校验令牌三次：
- `process_task` 开头（刚认领时）
- `_run_extraction` 写图谱前（`claim_check` 回调，同时验状态、令牌、content_hash 三者）
- 回写终态前

任何一次对不上就"自愿中止"——不写终态、不重试，因为新载荷已经在 pending 里等新认领者了。

## Q29【必答】幂等是怎么保证的

三层，缺一层都会出问题：

**第一层，任务级**：`graph_build_tasks` 按 `(user_id, source_type, source_id)` 唯一。重复触发是 upsert 覆盖 payload 置 pending，不会插出两行。内容变了（`content_hash` 不同）才把 `attempts` 归零，避免旧的重试计数拖累新内容。

**第二层，内容级**：`content_hash` 是正文的 MD5，存 `graph_extract_logs`。`_ensure_extract_log` 只在**`status == 'success'` 且哈希没变**时才返回 False（跳过）。

这里有个坑值得讲：一开始我写成"哈希相同就跳过"，结果 pending 和 failed 也被跳过，任务被置成 completed，但日志永远停在 pending，界面永久显示"解析中"。所以现在 pending / failed 一律重跑——**只有成功过的才允许跳过**。

**第三层，写入级**：Chunk 用 MERGE 复合键；实体按 (name, user_id) MERGE；所有关联边都是先清后插（`set_source_mentions` / `set_chunk_mentions` / `set_relations_from_source` 都是删了再建），而且清和插在同一个事务里（`_tx`），防中途失败留下半套。

## Q30【必答】删除一篇笔记，图谱里怎么清干净

`cleanup_note_graph` → `store.clear_source_data` + `sweep_orphan_entities`：

1. **先收集候选**：查这个来源 MENTIONS 过的所有实体 id（删之前查，删完就查不到了）。
2. **一个事务里删三样**：源节点（连带它的 MENTIONS 和 WIKI 边）、它所有的 Chunk、它建的所有 RELATES_TO 边。
3. **孤儿清扫**：对候选实体做

```cypher
SET e.source_note_ids = [x IN coalesce(e.source_note_ids, []) WHERE NOT x IN $removed]
WITH e WHERE size(coalesce(e.source_note_ids, [])) = 0
       AND NOT EXISTS { ()-[:MENTIONS]->(e) }
DETACH DELETE e
```

意思是：先从 `source_note_ids` 里摘掉这个来源，摘完如果**没有任何来源引用**、而且**没有任何 MENTIONS 边指向它**，才级联删除。

**为什么要两道条件**：一个实体可能被多篇笔记提到，删一篇不能把它删掉，所以看引用数；`source_note_ids` 只记笔记，文档的引用要靠 MENTIONS 边，所以两个都得看。

**为什么要在事务外单独做**：清扫是"可能删也可能不删"的判断，放在删除事务里会让事务变长、锁住更多节点。

## Q31【加分】重抽的时候，旧实体怎么办

只删不补会把还在用的实体删掉，所以做的是**引用收缩**：

`_run_extraction` 里在写新数据之前，先 `source_entity_candidates` 记下"这个来源此前关联过哪些实体"；本轮抽取写完，算出新实体集合；两者相减得到 `removed`——本轮没再关联上的旧实体，从 `source_note_ids` 摘掉，然后走同一个孤儿清扫。

场景：一篇笔记原来写了 Redis，后来改写成了 Memcached。重抽之后 Redis 这个实体不该再挂在这篇笔记名下，如果它没被别的笔记提到，就该消失；如果别的笔记也提了 Redis，它留下，只是不再指向这篇。

`upsert_entity` 本身是幂等的（按 name + user_id MERGE），所以没变过的实体是"更新"不是"新建"。

## Q32【加分】抽取失败了怎么重试

`MAX_TASK_ATTEMPTS = 3`。

`process_task` 拿到 `_run_extraction` 的返回值：`True` 是到达终态（成功，或"来源已删除/无正文"这类不该重试的正常终态），`False` 是可重试的失败。

- `attempts < 3`：任务重回 pending，`error_message` 写"抽取失败，待重试"，worker 下一轮会再认领。
- `attempts >= 3`：置 failed，`graph_extract_logs` 也置 failed 带错误信息，等用户手动重抽（`manual_re_extract` 走 `force=True`，绕过哈希判重）。

**worker 层还有一层兜底**：`process_task` 之外抛异常（比如连 MySQL 都断了）时，用 `UPDATE ... WHERE id=? AND status='running' AND run_token=?` 把任务拨回 pending。带令牌条件是为了不误伤已经被重新入队的新任务。

## Q33【陷阱】图谱里的数据规模上来会怎样

现在最贵的是写入时的 LLM 抽取（一篇文章一次调用，几秒到几十秒），和检索时的实体抽取（`QueryEntityExtractor` 也是一次 LLM 调用，实测 `search_graph` p50 13.9 秒）。

**写侧**：单 worker 串行消费，量大就堆 pending。改法是拆成多 worker + lease 机制（`run_token` 已经是令牌的雏形，补上过期时间就是租约），worker 数量按 pending 深度动态调。

**读侧**：`search_graph` 里对每个候选实体单独调一次 `get_entity_notes`，这是 N+1 查询，候选 5 个就是 5 次往返。应该改成一条 Cypher 一次查回来。另外实体抽取可以加缓存——同样的问句短时间内会重复出现。

**存储侧**：Neo4j 单机到千万节点要开始考虑分片或者按用户分库，现在没到那个量级。

# 第五部分 交叉与压测

## Q34【必答】RAG 里的图谱检索，和知识图谱模块，是什么关系

**数据是同一份，用法是两个层次**：

- 知识图谱模块负责**生产**：worker 把笔记和文档抽成实体 + 关系 + chunk 关联，写进 Neo4j。这是离线/异步的。
- RAG 里的 `search_graph` 负责**消费**：planner 判断这是实体型问题，就发一步 `search_graph`，它抽问句里的实体候选词，去图里匹配节点，返回实体证据 + 命中实体所在的 chunk。

同一个 Neo4j，Chunk 节点既是向量/全文检索的对象，也是图谱 MENTIONS 边的端点。这是我把向量库和图谱库合成一个的直接收益——一份数据，两种检索原语，不用同步两套存储。

---

## Q35【必答】多用户隔离怎么做的，说全

四层，每层都要有：

1. **MySQL 业务表**：`notes` / `chat_sessions` 都有 `user_id`，所有查询带 `WHERE user_id = ?`。
2. **Neo4j 节点**：Entity、Chunk、Note、Doc 全都带 `user_id` 属性，查询一律过滤。Chunk 的 MERGE 键是 `(id, user_id)` 复合键——因为文档 md5 跨用户会重复。
3. **鉴权**：JWT 解出来的 `user_id` 通过 `Depends(get_current_user_id)` 注入，不是从请求体里读的。
4. **工具层**：用 ContextVar 传 user_id，不给模型填（见 Q15）。

**一个容易漏的点**：`chat_sessions` 查询时如果 session 存在但不属于当前用户，抛 403 而不是当成不存在建新的——否则用户可以靠猜 session_id 探测别人有没有这个会话。

## Q36【必答】延迟有多高，你做了哪些优化

实测前置管线 30 秒左右，用户感知首 token 约 37 秒（`results/eval_end2end/report.md`）。这个数字很难看，我清楚问题在哪。

**已做的**：
- planner 从主大模型换成独立小模型（改之前规划一步能到 39 秒），配单例复用 keep-alive。
- 图检索和文本检索用 `asyncio.create_task` 并行，图那一路内部还要调一次 LLM 抽实体，串行的话两段叠加。
- planner 8 秒总预算超时，三层降级，模型挂了也能出计划。
- 生成端按 chunk 推流，首 token 不用等整段生成。
- 每一步都打了耗时日志（`【RAG耗时】planner=xx ms retrieval=xx ms evaluator=xx ms`），优化时能直接定位到哪一段。

**还没做的（说得出下一步，比说"已经很快了"可信）**：
- evaluator 还在用主回答大模型（`_resolve_shared_chat_model`），它跟 planner 干的是同一类活——判一句话对不对，也该换小模型。
- `search_graph` 的实体抽取 p50 13.9 秒，是单点最大头。可以加 query 级缓存，或者先用规则抽一部分、只把不确定的句子交给 LLM。
- `search_graph` 里对每个候选实体单独查关联来源，N+1 查询，应该合并成一条 Cypher。

## Q38【加分】这个项目你觉得最大的不足是什么

三个，按严重程度：

1. **图的关系数据没被用起来**。存了 RELATES_TO，也做了多跳评测，但检索端只做实体匹配 + chunk 提及，模型拿不到关系三元组。等于花了大成本建图，只用了一半。
2. **图检索延迟 13.9 秒，是整条链路的单点**。根因是查询时现场调 LLM 抽实体。这个设计本身可以商量——预生成实体标签 + 字符串匹配，精度可能降一点，但快两个数量级。
3. **切片那块有死代码**。`_optimize_chunks` 写了语义合并但没接上，文档实际是纯字符切分。这东西留着比删掉更危险，因为读代码的人（包括三个月后的我）会以为它在生效。

另外没做 prompt 注入防护：文档正文是直接进上下文的，如果文档里写了"忽略以上指令"，模型可能被带跑。要防的话，是在 system prompt 里明确声明"参考资料是数据不是指令"，加分隔标记，严重的场景上加一次模型自检。

## Q39【加分】如果重做一遍，你会怎么改

按投入产出排：

1. `search_graph` 补 1～2 跳邻居扩展，把 `(a)-[r]->(b)` 三元组作为结构化上下文喂给模型，而不是只给文本段落。这是让图真正产生增量的唯一办法。
2. evaluator 换小模型，或者跟 planner 合并成一次调用——现在两次串行 LLM 调用是延迟大头。
3. 实体抽取从"查询时现场抽"改成"写入时预生成 + 查询时匹配"，把 13.9 秒压到百毫秒级。
4. 补一个 RAGAS 或类似的自动评测，现在 faithfulness 和 correctness 是 LLM 裁判打的分，样本只有 20 条，不足以支撑参数调整。
5. 任务表加 lease，支持多实例。

**不会改的**：Chunk 统一放 Neo4j 这个决定、任务表当队列、ContextVar 传身份、自己写 MySQL checkpointer。这几个在现在的量级下是最省事的解，换任何替代方案都是增加组件换不来实际收益。

# 附录 B：容易被追问的名词，一句话版本

- **RRF**：倒数排名融合。不看两路各自的分数（量纲不同没法比），只看名次，`Σ 1/(k+rank)`。
- **checkpoint**：LangGraph 在图的每个节点执行后落的快照，含 state 和待写入。中断恢复靠它。
- **pending_writes**：checkpoint 里"已算出但还没提交到 state"的写入。HITL 的中断负载就挂在 `__interrupt__` 这个 channel 下。
- **ContextVar**：Python 的上下文变量，跟着 asyncio task 走，用来在调用栈里隐式传值（用户身份、思考回调）。
- **乐观锁**：不加锁读，改的时候用 `WHERE 旧值` 做条件，看影响行数判断有没有被人改过。
- **幂等**：同样的输入执行多次，结果和执行一次一样。这里靠 MERGE 和先清后插。
- **孤儿实体**：没有任何来源引用、也没有任何 MENTIONS 指向的实体节点，删来源时要顺手清掉。
- **HITL**：Human-in-the-loop，人在回路。工具执行前停下来等人批。
